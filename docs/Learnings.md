Durable, non-obvious knowledge about this project. See [[../AGENTS.md]] for operational rules.

## LVGL display pipeline (added 2026-09)

### Color depth must be 32-bit
The LTDC layers are configured as `LTDC_PIXEL_FORMAT_ARGB8888` by the BSP
(`stm32469i_discovery_lcd.c`, `BSP_LCD_LayerDefaultInit`) and the OTM8009A panel is
initialized in RGB888 mode. LVGL therefore renders with `LV_COLOR_DEPTH 32`.
An earlier `lv_conf.h` said 16 (RGB565) — that would produce garbage colors on this
pipeline, even though it "compiles fine".

### SDRAM layout (16 MB @ 0xC0000000)
| Region | Address | Size |
|---|---|---|
| Framebuffer 1 (active LTDC layer) | `0xC0000000` | 800×480×4 = 1,536,000 B |
| Framebuffer 2 (back buffer) | `0xC0180000` | 1,536,000 B |
| LVGL heap (`LV_MEM_ADR`) | `0xC0300000` | 8 MB → ends `0xC0B00000` |

The LVGL heap **must** be placed in SDRAM via `LV_MEM_ADR`: with the default builtin
stdlib and no `LV_MEM_ADR`, LVGL creates an 8 MB *static array* that cannot fit in the
F469's ~640 KB internal RAM (link failure).

### Why we don't use LVGL's stock ST LTDC driver (`LV_USE_ST_LTDC`)
`lv_st_ltdc.c` requires `USE_HAL_LTDC_REGISTER_CALLBACKS=1`, but this framework's
`stm32f4xx_hal_conf.h` hard-codes all `USE_HAL_*_REGISTER_CALLBACKS` to 0 **unconditionally**
(no `#ifndef` guard), so a `-D` build flag cannot override it. A project-local
`hal_conf.h` also can't shadow the framework's, because C quoted-includes search the
including file's own directory first. Instead, `src/lvgl_display.c` implements the same
direct-mode protocol in ~80 lines: LVGL renders into two SDRAM framebuffers; on the last
flush of a refresh we call `HAL_LTDC_SetAddress_NoReload()` +
`HAL_LTDC_Reload(LTDC_RELOAD_VERTICAL_BLANKING)` and spin in the flush-wait callback until
the register-reload-complete flag (`RRIF`) is cleared by our own `LTDC_IRQHandler`.

Consequences to remember:
- `LTDC_IT_RR` must be enabled after LCD init (done in `lvgl_display_init()`).
- The project defines its own `SysTick_Handler` and `LTDC_IRQHandler` — there is no
  `stm32f4xx_it.c`. Any new peripheral IRQ needs a vector entry added by hand.
- The flush-wait spin blocks the main loop for up to one vertical blanking period per
  frame; UART byte-polling pauses during that window (fine at current packet rates).

### LVGL 9.5 config gotchas hit in this project
- **A theme must be initialized explicitly.** Without `lv_theme_default_init()` +
  `lv_display_set_theme()`, widgets get no visible styles: button backgrounds are transparent
  and label text falls back to the default black — on a dark UI the screen looks blank even
  though LVGL is running (only explicitly styled objects, e.g. white title text, show up).
- Font sizes need explicit `#define LV_FONT_MONTSERRAT_<size> 1` in `lv_conf.h` (font `.c`
  files are self-guarded); the theme uses 14, the screen title uses 28.
- `LV_TICK_CUSTOM` no longer exists in v9 — feed `lv_tick_inc(1)` from the SysTick handler.
- Button "click" is `LV_EVENT_SHORT_CLICKED` (generated by indev on quick press+release);
  simulating a press = `lv_obj_send_event(btn, LV_EVENT_SHORT_CLICKED, NULL)`.

## PlatformIO / build gotchas

### Local libs are copied into `.pio/libdeps/`
Editing files under `lib/stm32_bsp/` has **no effect** until the stale copy at
`.pio/libdeps/disco_f469ni/stm32_bsp/` is removed (`rm -rf .pio/libdeps/disco_f469ni/stm32_bsp`).
The build silently compiles the old copy. `.pio/` is gitignored, so deleting it is safe.

## Clock configuration (HSE crystal mismatch) — fixed 2026-09

The board is an STM32469I-DISCO **revC with an 8 MHz HSE crystal**, but the framework
hardcodes `HSE_VALUE = 25 MHz` in three places (`stm32f4xx_hal_conf.h`,
`system_stm32f4xx.c`, `stm32f4xx_ll_rcc.h`). The PLL tree (M=8, N=360, P=2) is valid for an
8 MHz input and the chip really runs at **180 MHz SYSCLK** — proof: ST's own BSP DSI-PLL
config (`stm32469i_discovery_lcd.c`, non-REVA branch `PLLDIV=125/IN_DIV2`) only yields the
designed 500 MHz VCO from an 8 MHz crystal (the REVA branch uses N=100/IDIV=5 for its 25 MHz
one), and UART reads cleanly with BRR computed for APB1 = 45 MHz.

The wrong constant had two real effects, not just cosmetic:
1. **SysTick stretch** — `HAL_RCC_ClockConfig()` reconfigures SysTick from the reported
   (bogus) 562.5 MHz, so each "tick" took 3.125 ms of wall time and every `HAL_Delay`/timeout
   ran ×3.125 slower (a 1000-tick DSI timeout = 3.125 s). This was the main cause of the
   multi-second boot silence after SDRAM/LCD init was added.
2. **Out-of-spec DSI PHY bit period** — `HAL_DSI_Init()` computes the HS unit interval from
   HSE_VALUE; with 25 MHz it wrote UIX4=2 (a 2 GHz request) instead of the designed UIX4=8
   (500 MHz). The link apparently still worked, but that's undefined behavior.

**Fix:** `-DHSE_VALUE=8000000UL` in `platformio.ini` build_flags — all three framework
definitions are `#ifndef`-guarded, so one flag overrides them. SysTick is now true 1 ms and
the DSI PHY config is correct; the old manual USART3 BRR workaround in
`MX_USART3_UART_Init()` was removed (HAL computes it correctly). Do not remove this flag —
boot timing and DSI behavior silently regress. Keep the REVA branches (`PLLM=25`, DSI
N=100/IDIV=5) as-is; they're for revA's 25 MHz crystal.

Boot-time cost to know: `LCD_ReadType()` probes NT35510 first (this board has an OTM8009A),
so every boot eats one DSI read timeout (~1 s nominal). If faster boot is ever needed, patch
the BSP copy to skip that probe — mind the `.pio/libdeps` stale-copy rule above.

### Framework package incident (2026-07 → removed 2026-09)
A previous session left `dbg_print("ok")`/`dbg_print("timeout")` calls inside
`DSI_ShortWrite()` in the **global** framework package
(`~/.platformio/packages/framework-stm32cubef4/.../Src/stm32f4xx_hal_dsi.c`). It was invisible
in this project only because UART3 used to be initialized after LCD init, and it would break
any other project lacking a `dbg_print` symbol. Removed; if you see unexpected per-DSI-write
UART spam or link errors for `dbg_print`, check that file first.

## Debugging notes

### ST-LINK / openocd (dev build 0.12) quirks observed
- A manual `openocd -c "init; reset run"` session can leave the target **held in reset**
  (symptom: no UART output at all, PC reads as `Reset_Handler`, later halts fail with
  "target was in unknown state"). Recovery that worked: `st-flash --reset read <f> 0x08000000 16`.
- `pio run -t upload` (openocd) resets the target correctly and reliably.
- Plain `cat /dev/ttyACM0` was flaky in this environment; Python pyserial
  (`~/.platformio/penv/bin/python`, `serial.Serial('/dev/ttyACM0', 115200, timeout=N)`)
  read the VCP reliably.
